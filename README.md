# mapcidade-metadata-publisher

> Anonymized, from-scratch reconstruction of a real internal tool's architecture, built for a portfolio. Fictional data only ("MapCidade" / Rivermeadow) — no real company, city, or infrastructure is represented here.

## English

### Problem

Registering a new GIS theme — or copying an existing one to another profile, or moving one across databases entirely — means writing coherent rows into half a dozen central tables at once (a table registry, the theme itself, its map-tree node, its WMS params, its data dictionary, its permission grants), respecting parent/child hierarchy and display order. Done by hand, it's easy to leave one table out of sync with the others, producing a theme that's broken or inconsistent between profiles.

### Solution

A guided form collects the theme (or the copy/transfer) parameters, and a planner generates the full SQL plan for every table involved at once, preserving order and hierarchy. Every write goes through a two-step gate: it always runs in dry-run first, showing exactly what would change, and only writes for real once the operator explicitly types "EXECUTE" — a 409 guard rejects `execute: true` without that confirmation before the tool even opens a database connection.

### Stack

TypeScript — Express 5 backend (`src/`) + Next.js 16 / React 19 frontend (`frontend/`), direct `pg` for database access and `ssh2` for an optional tunnel, `zod` payload validation. Backend: 32 vitest tests. Frontend: standard portfolio dark UI (`Brand`, tab layout), production build verified.

### How to run

Backend:
```bash
npm install
npm run dev      # tsx watch src/index.ts (port 3340)
npm test
```

Frontend, in `frontend/`:
```bash
npm install
npm run dev      # next dev (port 3010)
```

Point `NEXT_PUBLIC_API_BASE` (see `frontend/.env.example`) at the backend if not running on the default port.

### Demo

Terminal + browser walkthrough — dry-run preview, 409 guard, and the "EXECUTE" confirmation flow; a recorded GIF will be linked here.

### Execution gate (dry-run by default)

Every write route uses a gate (`executeGateSchema`, in `src/schemas.ts`): without `execute: true` the call only returns the SQL plan that would run. With `execute: true`, `confirm: "EXECUTE"` is mandatory — otherwise the API refuses the operation (`ConfirmationError`, HTTP 409 guard) before even opening a database connection.

### What I learned / engineering decisions

The real tool consolidates two prior generations (a discarded desktop GUI, then a Flask/NiceGUI web app) behind one `Db`-style interface already designed for injectable testing — the planner functions never talk to `pg` directly, they take a `Queryable` and return a `Plan` (an ordered list of SQL statements with symbolic `$ref` placeholders for values generated by earlier `RETURNING` clauses). That separation is what makes the whole thing testable without a live Postgres connection, and it's also what made the anonymization pass mechanical: table and column names (`theme`, `map_node`, `map_param`, `data_dictionary`, `permission`, ...) are invented generics standing in for the platform's real internal schema, not the schema itself — the planning/execution logic is untouched.

One thing worth calling out from the original design: primary-key column names for the permission table are checked against three historical spellings (`perm_id` / `legacy_perm_id` / `id`) — different environments named it differently over time, and the planner tolerates all three rather than assuming one. That's a real "schema drift across long-lived installs" pattern, not an artifact of anonymizing this repo.

## Português

### Problema

Cadastrar um tema novo — ou copiar um existente pra outro perfil, ou movê-lo entre bancos — significa escrever linhas coerentes em meia dúzia de tabelas centrais ao mesmo tempo (um registro de tabela, o tema em si, seu nó na árvore de mapas, seus parâmetros WMS, seu dicionário de dados, suas permissões), respeitando hierarquia pai/filho e ordem de exibição. Feito manualmente, é fácil deixar uma tabela desalinhada com as outras, gerando um tema quebrado ou inconsistente entre perfis.

### Solução

Um formulário guiado coleta os dados do tema (ou da cópia/transferência) e um planner gera o plano de SQL completo para todas as tabelas envolvidas de uma vez, mantendo ordem e hierarquia. Toda escrita passa por um gate de duas etapas: sempre roda em dry-run primeiro, mostrando exatamente o que mudaria, e só grava de fato quando o operador digita "EXECUTE" explicitamente — um guard 409 recusa `execute: true` sem essa confirmação antes mesmo de abrir conexão com o banco.

### Stack

TypeScript — backend Express 5 (`src/`) + frontend Next.js 16 / React 19 (`frontend/`), `pg` direto pro banco e `ssh2` pra túnel opcional, validação de payload com `zod`. Backend: 32 testes vitest. Frontend: UI escura padrão do portfolio (`Brand`, layout em abas), build de produção validado.

### Como rodar

Backend:
```bash
npm install
npm run dev      # tsx watch src/index.ts (porta 3340)
npm test
```

Frontend, em `frontend/`:
```bash
npm install
npm run dev      # next dev (porta 3010)
```

Aponte `NEXT_PUBLIC_API_BASE` (ver `frontend/.env.example`) pro backend se não estiver na porta padrão.

### O que aprendi / decisões de engenharia

A ferramenta real consolida duas gerações anteriores (uma GUI desktop descartada, depois um app web Flask/NiceGUI) atrás de uma interface estilo `Db` já projetada pra ser testável por injeção — as funções de planejamento nunca falam com `pg` direto, recebem um `Queryable` e devolvem um `Plan` (lista ordenada de statements SQL com placeholders simbólicos `$ref` pra valores gerados por `RETURNING` anteriores). Essa separação é o que torna tudo testável sem conexão real com Postgres, e foi o que tornou a anonimização mecânica: nomes de tabela e coluna (`theme`, `map_node`, `map_param`, `data_dictionary`, `permission`, ...) são genéricos inventados no lugar do esquema interno real da plataforma, não o esquema em si — a lógica de planejamento/execução ficou intocada.

Uma coisa que vale destacar do design original: os nomes de coluna de chave primária da tabela de permissão são checados contra três grafias históricas (`perm_id` / `legacy_perm_id` / `id`) — ambientes diferentes batizaram isso de formas diferentes ao longo do tempo, e o planner tolera as três em vez de assumir uma. É um padrão real de "desvio de esquema entre instalações de vida longa", não um artefato da anonimização deste repo.
